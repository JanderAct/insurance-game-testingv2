### Why these, and not others

Honest answer, by category — and the first entry is the important one:

- **⚠ React + Vite + TypeScript + Tailwind was NOT a decision. It is Bolt's
  default template.** The stack arrived with the scaffold that **Bolt
  (bolt.new / StackBlitz)** generated at the very start of the project (§0), and
  it was inherited and kept. Nothing was evaluated and nothing was rejected.
  Read it as a starting point nobody had reason to revisit, not as a considered
  fit to the problem.

  The template is still visibly present. `vite.config.ts` is **byte-identical**
  from the founding commit to HEAD, including the line that gives it away:

  ```js
  optimizeDeps: { exclude: ['lucide-react'] }
  ```

  `lucide-react` is an ordinary icon package that needs no such exclusion — the
  line is template boilerplate that survived two months because nothing ever had
  cause to look at it. Ten files in total are byte-identical from that upload to
  HEAD; see `source-provenance.md` §1.1 for the list and the corroborating
  package-manager evidence.

- **⚠ `@supabase/supabase-js` was not a decision either.** It is a Bolt template
  default, present in the founding `package.json` as one of only four
  dependencies, and it has never been used — no import, no client, no
  configuration. It does **not** indicate that a backend was ever planned.
- **`lucide-react`** — likewise a Bolt template default rather than a chosen
  icon library, though it is now genuinely used in 17 files.
- **`xlsx`** — a real choice, and one of the few: the deliverable is a
  spreadsheet a risk manager opens in Excel, and it is the de-facto library for
  that in JS. Apache-2.0.
- **`fflate`** — the best-documented choice in the project. Selected after a
  measured bake-off against `lz-string`, recorded in full in the header of
  `src/utils/gameSave.ts`. `lz-string` won on compression ratio and lost on
  speed by roughly 10×; `fflate`'s base64 output is ASCII, which makes the
  stored byte count equal the string length and the size gate exact.
  `lz-string` was installed for that measurement and removed again — see
  `source-provenance.md`.
- **`marked`** — a conventional choice for its job; no evaluation recorded.

**The pattern worth carrying forward:** of the seven runtime dependencies, three
(`react`, `react-dom`, `lucide-react`) plus the entire build toolchain came in
with the scaffold, one (`@supabase/supabase-js`) came in with it and was never
used, and only `xlsx`, `marked` and `fflate` were added deliberately. A team
proposing to change the stack is not overturning a decision — there was none.

There is **no** test framework (no Jest, Vitest, Playwright, Testing Library).
Verification is done by 89 hand-written diagnostic scripts run as a sweep. See
§4.

## 2. OVERALL STRUCTURE

**A single-page browser application with no backend, no database and no network
calls.** Everything runs client-side. There is no server component to deploy,
no API to authenticate against, and no data leaves the browser.

```
                    ┌────────────────────────────────────────┐
                    │  BROWSER (the entire application)      │
                    │                                        │
   index.html ──▶   │  main.tsx                              │
                    │    └─ App.tsx  (all state, all routing)│
                    │         ├─ 12 pages (tab-switched)     │
                    │         ├─ 9 shared components         │
                    │         │                              │
                    │         ├──▶ src/utils/  (the engine)  │
                    │         │      simulationEngine.ts     │
                    │         │      claim engines (WC/GL/PR)│
                    │         │      reinsurance, reserving, │
                    │         │      membership, pricing     │
                    │         │                              │
                    │         ├──▶ src/data/   (constants)   │
                    │         │      calibrated parameters,  │
                    │         │      200-member catalogue    │
                    │         │                              │
                    │         └──▶ localStorage              │
                    │                key riskpool_gamestate_v10
                    │                DEFLATE + base64        │
                    └────────────────────────────────────────┘
                                     │
                                     ▼  (user-initiated download only)
                            .xlsx / .csv files
```

**There is no frontend → backend → database → external API chain.** The diagram
above is the whole of it. The only egress is a file the user chooses to
download.

### Routing

There is none, in the router sense. `App.tsx` holds an `activeTab` string in
React state and renders one of twelve pages by conditional. No `react-router`,
no URL routing, no deep links. Refreshing the browser returns the user to the
dashboard of their restored game.

### State management

There is none, in the library sense. No Redux, no Zustand, no Context. All game
state lives in `useState` hooks inside `App.tsx` and is passed down as props.
`App.tsx` is the single source of truth and is correspondingly large.

## 3. THE ENGINE — how a simulated year is computed

This is the part a dev team cannot reconstruct quickly, so it is described
rather than left to the code.

`src/utils/simulationEngine.ts` (≈4,000 lines) exposes `processYear(gameState,
decisions)`. One call advances the pool one year. Per active coverage line
(Workers' Compensation, General Liability, Property) it:

1. **Prices** the line — a funding target from a confidence level selected on a
   calibrated CLF (confidence level factor) curve, times exposure, times class
   relativities, times each member's experience modifier.
2. **Generates claims** — a per-line generator draws individual claims from
   fitted severity mixtures. `wcClaimEngine.ts`, `glClaimEngine.ts`,
   `propertyClaimEngine.ts`. These produce a **claim register**: individual
   claims with ids, member attribution, accident year, and gross ultimate.
3. **Applies the reinsurance tower** — per-occurrence excess layers with
   attachments and limits, plus an aggregate stop for two lines.
4. **Books reserves** — claims are grouped into an accident-year **cohort**
   which is booked with an optimistic markdown that unwinds over a horizon, and
   develops stochastically year over year (the "IBNER" mechanism).
5. **Moves membership** — retention probability from price change, dividends,
   assessments and surplus; which members leave is decided by an adverse
   selection model in `memberDeparture.ts`; the pool may also decline to renew
   members above an experience-modifier threshold
   (`renewalUnderwriting.ts`).
6. **Settles financials** — investment income, expenses, dividends or
   assessments, loans between lines, and surplus.

**Randomness is seeded and reproducible.** `src/utils/random.ts` provides a
seeded PRNG; a game is identified by an `instanceId` from which the seed is
derived, so the same id replays the same game exactly. This property is load-
bearing: several gates assert bit-identical results across runs.

**A pre-game past is simulated before year 1.** `priorHistoryEngine.ts` runs
`MATURATION_YEARS = 7` years to build an opening book, then three further
"declared" pre-game years that the player can see. The seven maturation years
are deliberately *not* retained — this has consequences documented in
`data.md` and `known-issues.md`.

## 4. VERIFICATION ARCHITECTURE

There is no unit test suite. Instead `scripts/diagnostics/` holds **89
standalone TypeScript programs**, each of which imports the real engine, runs
it, asserts properties, and exits non-zero on failure. `scripts/gates.ts` is a
runner that executes them in parallel and enforces a manifest.

Three tiers, declared in `scripts/gates.ts`:

| Tier | Count | Purpose |
|---|---|---|
| FAST | 52 | Runs every commit. Measured 5m59s wall at 3-way concurrency. |
| SLOW | 13 | Runs before a merge. ~77 min CPU. |
| PROBES | 24 | Not gates — generators and readings that assert nothing. |

**The manifest check is the load-bearing part.** It fails if any file in
`scripts/diagnostics/` is absent from all three lists, if a gate is listed
twice, if a listed gate is missing from disk, or (added at `62e0481`) if a gate
in FAST has a recorded runtime above `TIER_THRESHOLD_SECONDS = 88` or no
recorded runtime at all. Runtimes live in `scripts/gate-timings.json`.

Two **baseline** files act as regression locks:

- `baselines/VALUE_IDENTITY_v37.json` (1.76 MB) — every finite numeric field on
  every line and pool result across 3 seeds × 4 line configurations × 5 years.
  `value-identity-check` compares against it field by field.
- `baselines/SOLO_EXPORT_GUARD_v37.json` — SHA-256 of 24 exported CSVs.

These answer different questions (values vs. shape) and both are kept
deliberately.

## 5. BUILD AND TOOLING CONFIGURATION

- `vite.config.ts` — Vite + React plugin. **This is the Bolt scaffold's file, unmodified**: byte-identical from the founding commit to HEAD, `optimizeDeps.exclude: ['lucide-react']` and all.
- Three TypeScript configs: `tsconfig.app.json` (the `src/` build, targets
  ES2020, DOM libs), `tsconfig.scripts.json` (the diagnostics, targets ES2022,
  includes DOM libs deliberately because scripts import `src/` files that use
  `structuredClone`), `tsconfig.node.json`.
- `tailwind.config.js` + `postcss.config.js` + `autoprefixer` — standard
  Tailwind pipeline, **scaffold-supplied**. `postcss.config.js` and
  `src/index.css` (three bare `@tailwind` directives) are both unchanged since
  the founding commit; `tailwind.config.js` is the one that has been edited.
- `eslint.config.js` — flat config, `js.configs.recommended` +
  `typescript-eslint` recommended + React hooks/refresh plugins. **Also
  unchanged since the founding commit** — which is why it still declares
  `eslint-plugin-react-hooks` at a release-candidate version.

`npm run lint` reports **21 problems (14 errors, 7 warnings)** at `62e0481`;
6 are auto-fixable. `npm run typecheck` passes clean on both projects. See
`known-issues.md` §6.5 for the breakdown.

Per the spec's question, and expanded in `source-provenance.md`:

- **The entire codebase** is AI-generated, by **three tools in sequence** —
  Bolt, then Codex/ChatGPT, then Claude Code — as established in §0.
- **The scaffold and build configuration are Bolt (bolt.new / StackBlitz)
  output**, and ten files are still byte-identical to it at HEAD, including

  `tsconfig`s, `src/main.tsx` and `src/index.css`. Full list and evidence in
  `source-provenance.md` §1.1.
- **`src/data/memberCatalog.ts`** is a generated file — it says so in its first
  line — produced by `scripts/tools/generate-member-catalog.ts` from
  `src/data/roster_canonical_v6.csv`.
- **`src/data/wcClfGrid.ts` and `src/data/glClfGrid.ts`** hold numeric grids.
  The WC grid is *derived* by a script in the repo (`wc-clf-grid-derive`); the
  GL grid is described in `src/data/clfTables.ts` as **"SUPPLIED — a real
  pool's measured curve"**. That distinction matters and is flagged in
  `source-provenance.md`.
- No code was knowingly copied from Stack Overflow, blogs, tutorials or other
  repositories. No such attribution appears anywhere in the tree. **This cannot
  be positively verified** — an AI model may reproduce patterns from its
  training data without signalling it. See `source-provenance.md`.

N/A: there are no vendored third-party source files, no `lib/` of copied code,
no minified bundles checked in, and no git submodules.
